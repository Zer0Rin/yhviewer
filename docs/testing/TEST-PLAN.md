# YHViewer 测试计划（1.0.0 之后）

建议放进仓库 `docs/testing/TEST-PLAN.md`，替代 `outputs/v1.0/DEVICE-TEST-PLAN.md`（那份是 1.0 一次性用的验收清单）。

## 0. 为什么重写

1.0 验收有两个问题：

- **测得太细**。逐帧录屏、毫秒时序、每项都测两个包、补测历史未测项……花了大量时间，却没有抓到真正的问题。
- **该跑的自动测试没跑**。模拟器仪器测试只在推送 main 时运行，PR 上会跳过。所以 FIX1–FIX6 合并前一次都没跑过，合并后才发现 19 项失败（其中 11 项早就坏了，也一直没人注意）。

新计划的原则：

1. **能自动测的就不在手机上测。** 真机只测自动化测不到的部分：系统选择器、分享和"打开方式"、真实 WebView 版本、手感。
2. **按改动范围决定测什么**，而不是每次全量测试。
3. **真机发布清单控制在 1 小时内**。只判断"通过 / 失败 / 阻塞"，不量毫秒、不逐帧分析。只有当改动本身针对性能或动画时，才做对应的测量。
4. **发现失败就停下汇报**，不自己修，不扩大范围。

## 2. 测试分层：什么时候跑什么

| 层 | 内容 | 什么时候 | 谁来做 |
|---|---|---|---|
| **L0 本地** | 改到的模块的单元测试 + `test-flow-shell.cjs` | 每次提交前 | 写补丁的人（我或 Codex） |
| **L1 PR CI** | 全量单元测试、Lint、权限检查、flow 模型 | 每个 PR，自动 | CI |
| **L2 仪器测试** | 全量仪器测试，Strict 和 Standard 都跑 | **合并前**：PR 改到下表"需要 L2"的范围时，在 PR 分支上手动触发 `ci.yml`（workflow_dispatch），通过后才能合并 | Codex 触发，结果写进 PR |
| **L3 真机清单** | 第 5 节，约 45 分钟 | 只在发布前跑一次，用最终源码构建的 RC 包 | Codex 操作，用户抽查 |
| **L4 发布流程** | `release.yml` | 打 tag 时 | CI |

L2 必须在合并前跑，这是这次最主要的教训。

| EPUB（解析、注入、`EpubCache`） | EpubTest 等 | 需要 | B 组 F4 |
| Markdown / 代码模板（`md/`、`code/`） | 模板测试 + 用 Chromium 跑一次真实复制/渲染 | 需要 | C 组 |
| 沙箱、权限、网络（`DocPermissions`、拦截、CSP） | 权限组合测试 | 需要，并检查 Standard 正向对照 | D 组全部 |

## 4. 当前待办：让仪器测试恢复全绿

这是 1.0.1 之前的第一件事，只改测试和 CI，不改应用行为。目标：两个版本在 main 上**连续两次**全部通过。

1. **原样重跑一次**失败的任务，不改代码，区分偶发失败和稳定失败。
2. **预期需要按新行为更新的**（已知 1 项，可能还有）：
   - `V11FlowAcceptanceTest.epubNativeInternalLinkJumpsChapterAndAnchor`：期望 `y=0`，实际 `96.9`。FIX4 有意让锚点停在顶栏下方，断言要改为"在顶栏下沿 ±2px，并且完全可见"，不能改成放宽误差；
   - 凡是断言"章节顶端在视口顶端"或"滚到章节顶端就算这一章"的，按 FIX5/FIX6 的规则改为以顶栏下沿为准。
3. **在旧代码上也失败的 11 项**：逐项判断是测试写错了（比如找不到"章节连续滚动"控件，可能是 v16 之后界面改了）、只在模拟器上不稳定，还是真 bug。前两种修测试；真 bug 记成 issue，写进 1.0.1 的范围。
4. **Standard 网络正向对照**：日志里加上实际的状态码。如果是 CI 网络问题，就改为失败时重试一次；仍失败的话，标为"环境不可用"并单独上报，不能静默通过。
5. **补上缺失的仪器测试**（FIX4–6 目前只有 JVM 测试和 flow 模型覆盖）：
   - 连续模式从目录跳到 F4 第 3 章，图片延迟加载后仍停在第 3 章；
   - 代码选区跨越空行，在 `<html>` 上派发 copy 事件后仍保留空行。
6. **CI 规则**：PR 改到第 3 节"需要 L2"的路径时，在 PR 描述里附上 L2 运行链接。可以先作为人工约定；要自动化的话，再给 `ci.yml` 加路径过滤。

做到第 3 步时停下汇报一次，再决定哪些属于 1.0.1。

## 6. 报告格式

一页就够：

```
版本 / 提交：
L1 链接：      L2 链接（Strict / Standard 通过数）：
真机：A1 ✓ A2 ✓ … （失败项：现象一句话 + 截图 + 复现步骤）
失败：N 项      阻塞：N 项（原因）
结论：可以发布 / 不能发布
```

不需要写历史记录、哈希逐项比较、像素差值和帧时间戳。APK 的 SHA-256 和签名证书只在发布那一步核对一次。

## 7. 边界（Codex 必须遵守）

- 只安装、卸载 `.rc.strict` 和 `.rc.standard`。正式包、`preview`、`qa.test` 一律不动。
- 只打开测试目录里的素材，不浏览、不截图个人文件。
- 签名密钥只走环境变量或 GitHub Secrets。临时测试密钥放在 `build/` 下，用完就删。
- 修改过的系统设置（字体、动画、旋转等），测完要恢复。
- 测试期间不改代码。发现问题就停下汇报，由用户决定是否修。
- 不推送 tag，不发布，不合并 PR，除非用户明确确认。
